Schools Product · Engine Architecture v2

Three ways to grow the lab down to grade 4

Studied the real lab first. The identity: an engine is a domain with its own accent; each engine runs in phases to a payoff; every method is a live instrument whose bespoke visualization reveals structure — not an explainer, not a calculator. The school product is the lower rungs of this same ladder.

Identity held constant in all three  ·  same shell as the 7 existing engines  ·  one accent per engine  ·  methods.html per engine, organized in phases  ·  each method = live input → bespoke live visual  ·  honest operation budgets  ·  client-side, no server  ·  every school engine ladders up into a university engine you already built.
SUGGESTION 1

Domain engines that ladder up — the “Lab Ladder”

Five new domain engines, each the school-tier twin of an existing university engine, each with its own phase-arc and payoff. A student climbs: Number → Algebra → Geometry → Data → Functions, and each top rung hands off to a university engine. Closest to the lab you already have — just longer at the bottom.

+ Strengths

  • Most faithful to the existing lab — same shape, just more rungs
  • Every topic has one home; teachers map it to a syllabus strand instantly
  • The ladder is the marketing: “from grade 4 to university, one lab”

− Trade-offs

  • 5 new engines × ~15 methods each = a lot to build
  • Risk of the lower rungs feeling like “school versions” unless each method has a real bespoke visual
  • Domain silos hide cross-domain ideas (a function is also geometry)
SUGGESTION 2

Through-line journey engines — the “Story Engines”

Instead of domain silos, five long narrative engines — each a single spine that crosses domains, unified by one mathematical idea, walked from G4 to a payoff that hands off to a university engine. This is exactly what Number Theory already does (divisibility → RSA), stretched across the whole school curriculum.

+ Strengths

  • Most on-brand — each engine is a story with a payoff, like Number Theory’s arc
  • A student sees where it’s going from G4 — the payoff is the motivator
  • Cross-domain by design: a function is also geometry, an equation is also a set

− Trade-offs

  • Harder for a teacher to find “quadratic equations” — it lives inside The Equation
  • Topics still need a syllabus index layered on top for school compliance
  • Five long engines can feel like five novels — a lot to finish each
SUGGESTION 3

Instruments that grow — the “Growing Instruments”

Five live instruments, each a single tool that gains capability levels as the student climbs grades — like a synth that unlocks more oscillators. Not a calculator: each level adds a new live visualization, so the same instrument a G4 pupil uses for arithmetic is, at level 10, solving non-linear systems on a graph. The escalation is the design.

− Trade-offs

  • Walks closest to the “just a tool” line you warned about — only the per-level visuals save it
  • A teacher can’t point at one engine for “circle theorems” — it’s Constructor L9
  • Each instrument must be designed for all grades up front (hard first build)
Recommendation

Take 1’s coverage, 2’s narrative, 3’s escalation — in layers.

Don’t pick one. Use Suggestion 1 (domain engines) as the structure and the ladder — that’s what gets built and what teachers map to. Engineer each engine as Suggestion 2’s through-line: every engine has a phase-arc to a payoff that hands off to a university engine, so a student always sees where it’s going. Borrow Suggestion 3’s escalation inside methods — a single method-instrument offers grade-leveled presets/capability, so the Sieve instrument a G6 pupil uses is the same surface that, at L10, runs Pollard’s rho in the Number Theory engine.

Structure = S1

Five school domain engines, each with its own accent, each a lower rung under a university engine. One topic, one home. This is the lab you already have, extended downward.

Narrative = S2

Each engine is written as a journey to a payoff (Number → “the real line”; Algebra → “solution sets have shape”; Geometry → “space = algebra”). The payoff is the hand-off to the university engine above.

Inside methods = S3

Don’t clone a method per grade. Build one live instrument with capability levels — the same Sieve, Factoriser, Plotter, Solver surface that gains power as the student climbs. Reuse, not duplication.

Syllabus view = a filter

Layer strand + grade-band filters on top (from the curriculum-scope doc) so a teacher can still ask “show me G7 Algebra.” The engines are the asset; the syllabus is a query over them.

Why this wins

You keep the lab’s real identity — domain engines, phase-arcs to a payoff, live method-instruments with bespoke visuals — and extend it downward instead of bolting on a “school site.” The school engines become the on-ramp into the 7 you already built, so the whole thing is one continuous lab from grade 4 to university. S3’s escalating instruments stop you from building thirty near-duplicate methods; S2’s payoffs stop the lower rungs from feeling basic. The only new cost is tagging each method with (strand, grade, instrument-level) — and you already have the strand + grade data.
