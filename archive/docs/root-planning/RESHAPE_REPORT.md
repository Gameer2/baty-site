# Reshape Report — The Lab / math-lab

**Date:** 2026-07-30
**Scope:** A read-everything audit and reshape proposal across four axes —
(1) code/file architecture, (2) the symbolic-kernel plan, (3) engine coverage/layout,
(4) design system / UI shell.
**Directive:** report only. Nothing was changed.

This report is the synthesis of a full read of the repo: the 13 kernel docs (`docs/kernel/00–12`),
all engine plans, `PLAN.md` / `CURRICULUM_ROADMAP.md` / `FOUNDATION_CHECKLIST.md` / `AUDIT_REPORT.md` /
`DESIGN_SYSTEM.md`, the shared core code (`engine-core.js`, `engine.css`, `proto.*`, `algorithms.js`,
`calc-core.js`, `cas-*`, `sympy-*`, `kernel/`, `tools/build-kernel-bundle.js`), all 9 engine directories,
and all ~153 `assets/js/` modules grouped by domain.

---

## 0. TL;DR — the one-paragraph state of the project

The Lab is a no-build-step, client-side computational math site of **9 engines** (Numerical flagship +
Calculus, Linear Algebra, Statistics, ODE, Optimization, Graph, Complex, Number Theory), sharing one
design system, two globals (`Engine`, `Proto`), and one CSS file. Pages are thin DOM wirings over
**pure, DOM-free cores** (`algorithms.js`, `calculus-symbolic.js`, `linalg-algorithms.js`,
`stats-algorithms.js`, `complex.js`, `number-theory.js`, `ode-symbolic.js`) that are also `require()`-able
by Node — this dual-consumption is the single best structural decision in the codebase. The symbolic
path is a **two-tier strangler fig**: a hand-rolled CAS kernel (`assets/js/kernel/`, 41 modules, L0–L4
built, L5 partial) backed by nerdamer+math.js and running off-main-thread in `cas-worker.js`, with a lazy
Pyodide-SymPy worker (`sympy-worker.js`) reached only after the hand-rolled classifier honestly refuses.
The kernel plan (`docs/kernel/`) is exceptionally detailed and internally consistent: measured baselines,
phase gates, the Rubi-not-Risch decision, server-hosted-for-secrecy target, and a load-bearing migration
contract. **The architecture is sound. The pain is at the delivery/duplication layer**, not the core:
hand-stitched `<script defer>` lists with no module system, triple-registration per method, a
duplicated CAS surface, scattered planning docs, inconsistent engine shapes, and 5 dead scratch files.

## 1. Code / file architecture

### 1.1 What exists today

- **No module system, no build step for app code.** Each of the 126 method pages hand-writes its own
  ordered `<script defer>` list: vendors → `engine-core.js` → domain core → `cas-client.js` (symbolic
  pages) → the page's own `<feature>.js`. There is one real build step, and it is narrow:
  `tools/build-kernel-bundle.js` wraps the 41 CommonJS kernel files into one `bundle.generated.js`
  (284 KB) because a browser worker has no per-file module scope and a naive `importScripts` collides
  (`Identifier 'Expr' has already been declared`). The bundle must be regenerated by hand after any
  kernel edit; `verify-cas-worker.js` asserts it has not drifted.
- **Two globals carry the page contract:** `Engine` (`engine-core.js`, chrome/KaTeX/Plotly/math-keypad)
  and `Proto` (`proto/proto.js`, hero particle field + 3D scenes + localStorage). Pages call
  `Engine.initChrome()` and `Proto.initRipple(canvas, accent)` on boot. Every `init*Scene` returns
  `{ dispose() }` and the page MUST dispose the previous handle before recreating (a real bug class,
  now fixed everywhere it applied).
- **Three runtime tiers** a page can land on, resolved by `cas-client.js`:
  1. **Worker** (default): `CAS.call` → `postMessage` to `cas-worker.js` (nerdamer + math.js + kernel
     bundle). Has a hard kill-switch: on timeout the worker is `terminate()`d and a fresh one spawns.
  2. **Sync fallback** (over `file://` or when `new Worker()` throws): runs the same engines on the
     main thread, no external timeout — relies on a cooperative `self.CAS_DEADLINE` wall clock.
  3. **SymPy fallback** (`sympy-client.js`): a *second*, separate worker booting Pyodide v0.26.4 + SymPy,
     reached only after the hand-rolled classifier refuses. Lazily spawned, 30 s timeout, no sync mode.
- **Pure cores are dual-consumed.** `algorithms.js` (≈40 numeric entry points), the symbolic cores, etc.
  expose a UMD `window.X` / `module.exports` so `tests/verify*.js` runs the *same* code in Node that the
  browser runs. 22 verify suites; the strong ones (`verify-linalg`, `verify-calculus`, the two CAS suites)
  assert invariants and behaviour, never string equality.

### 1.2 Assessment — what's good

- **The page-is-thin / core-is-pure split is the backbone.** It is what makes the strangler-fig rewrite
  safe (a kernel miss degrades to nerdamer, never worse) and what makes the test suites honest.
- **The CAS seam is already async and already a single point.** `cas-client.js:101` is the one place a
  page reaches symbolics; swapping `postMessage` → `fetch()` (server-hosted kernel) is contained there,
  and none of the 139 other modules notice. The kernel docs call this "the single luckiest fact about
  the current architecture" — accurate.
- **A system never verifies itself.** `verify-calculus.js` uses pure math.js finite differences because
  nerdamer's own `diff()` is wrong on √(quadratic) forms. This discipline is preserved in the kernel
  design (L4) and is the most valuable existing asset.

### 1.4 Reshape recommendations — code/file architecture

1. **Adopt a real module system for *app* code (ES modules + a tiny build), keep the no-build contract
   for pages if you insist.** The cleanest move is ES modules (`import`/`export`) + a single dev
   `esbuild`/`vite` bundler producing one `app.bundle.js` per engine, eliminating the 126 hand-stitched
   script lists (A1) and the manual kernel bundle (A2 partially). This is the one structural change with
   the largest leverage. If the no-build-step constraint is sacred (it is stated as identity in the
   docs), the alternative is a **method manifest**: one JSON per method declaring its dependencies, and
   a tiny generator emitting the `<script>` lists + the worker `OPS` table + the `CAS.*` wrappers + the
   verify cases from one source of truth — killing A1 and A2 without a runtime bundler.
2. **Unify the CAS to one contract.** Define a single `CAS` operation table (op → handler). Let the
   kernel/nerdamer path and the SymPy path both be *backends* behind it, dispatched by a fallback policy
   (kernel → nerdamer → SymPy → refuse), not two parallel client/worker pairs (A3). This also collapses
   triple-registration into one declaration (A2).
3. **Split `calculus-symbolic.js` by technique family** (rational integration / substitution / by-parts /
   partial fractions / series / multivariable / applications), each behind the same 24-entry-point
   facade so the migration contract is untouched (A4).
4. **Extract `poly.js` and `cx.js`** into shared `assets/js/shared/` consumed by every engine that needs
   them (A5, A9).
5. **Delete the 5 `imp-*.js` scratch files**, the stray PNG, and decide the fate of the 3 complex
   prototypes + the committed `bundle.generated.js` (regenerate on demand, gitignore it) (A6, A7).
6. **Replace the single global `failAll()` timeout with per-call budgets.** Keep the hard terminate for
   genuine hangs, but let a call declare an operation budget so budget exhaustion is a clean
   `{ok:false, partial}` refusal, not a fleet-wide kill (A8). This is required for Number Theory anyway.

| 4 full | Full Gruntz mrv, Puiseux, essential singularities; production wiring | ⚪ open |

### 2.2 The load-bearing decisions (constraints a reshape must respect)

1. **Assumptions (L1) come first and cannot be retrofitted** — the irreversible ordering constraint. R3b
   (inconsistent assumptions) is the *only* unsound path the L4 gate cannot catch, so contradiction must
   be detected at assertion time. Includes relational predicates (`x>a`, both sides symbolic), transitive
   closure, per-node `context` in the derivation tree.
2. **Rubi, not Risch** (MIT, curated ~100–200-rule subset, ported subtree-by-subtree gated by coverage).
   Technical choice = product differentiator: rule-based integration emits derivation steps as a
   byproduct. A full 6,600-rule port is explicitly rejected.
3. **Server-hosted kernel is the only real protection** (anything reaching a browser is recoverable).
   The split must be decided before Phase 1 *ships* (retrofitting a network boundary onto a
   synchronous-call kernel is painful). Kernel must be coarse-grained, serialisable, stateless, batched
   from day 1.
4. **The migration contract is sacred.** The 24 `CalculusSymbolic` + 10 `ODESymbolic` + 4
   `ComplexSymbolic` entry points must keep their signatures/return shapes. The
   `classify→rewrite→delegate→verify→refuse` shape is kept (only `delegate` changes).
   `verify-calculus.js` 809/809 is the regression net for the whole rewrite.
5. **L4 verification gate is mandatory:** never verify a system with its own primitives; never return an
   unverified result; refusal is first-class; `REFUSED→WRONG` is always a regression even if coverage rises.
6. **Syllabus-corpus closure is "done"** (100% of the Rubi subset, 0% silently wrong), not "complete CAS".
7. **Phase 2d determinism/bounded search is a gate** (not an optimisation): `normalize` idempotent on the
   terminating subset; output deterministic across runs *and* across rule-database reorderings; `maxSteps`
   (not wall clock) is the reproducible binding limit; peak expression size tracked per problem.
8. **Licence gate is hard:** MIT/BSD/Apache/CC-BY only; GPL and CC BY-NC forbidden; missing
   `*.LICENSE.txt` (math.js, GSAP, three.js) must be fixed before shipping.
9. **Honest refusals, not faked heuristics** for the deliberately-deferred scopes (ℚ(α)/LRT, full Gruntz,
   Puiseux/essential, Phase 4 production wiring).

### 2.3 Assessment — what's good

The plan is, frankly, better than most commercial CAS roadmaps: every claim is measured, every phase has
a runnable gate, the migration is strangler-fig (working software at every commit), and the worst
failure mode (silently wrong) is explicitly converted to refusal. The "one kernel, three engines" insight
(polynomial algebra + series machinery serve Calculus, ODE, *and* Complex) is correct and is the argument
for a kernel over three patched engines.

### 2.4 Assessment — what's unwieldy (reshape targets)

| # | Issue |
|---|---|
| K1 | **Doc sprawl.** The plan is split across `docs/kernel/00–12` (12 files), `SYMBOLIC_KERNEL_PLAN.md` (summary), `ANTIDERIVATIVE_STRATEGY.md`, plus per-engine plans (`CALCULUS_*`, `ODE_PDE_*` x2, `COMPLEX_*` x2, `NUMBER_THEORY_*`). The audit flags the roadmap as massively stale (26/30 Numerical items marked missing but actually built). `00_INDEX` itself says "send 00_INDEX, not the summary" — a sign the surface is too wide. |

| K4 | **ODE/PDE scope pivot is recent and under-propagated.** 2026-07-30 the target moved to `reference/ODE1/` course notes, away from the broader §5 syllabus; `laplace-transform.js` and `series-solution-fallback.js` are SymPy-only facades to be replaced by real hand-rolled engines. ### 2.5 Reshape recommendations — kernel plan

1. **Collapse the planning surface to one source of truth.** Keep `docs/kernel/00_INDEX.md` as the
   *only* entry; fold the per-engine plans into `08/09/10` (already exist) and delete the standalone
   `*_ENGINE_PLAN.md` duplicates once folded. Make `CURRICULUM_ROADMAP.md` a generated view from the test
   corpora + a status file, so "built" is a function of passing tests, not hand-edited emoji (K1, K2).
2. **Resolve the complex paradigm now** (K3): commit to V2 (two-plane mapping) as flagship and demote
   V1 domain-colouring to a supplementary view, or keep V1 and shelve V2. Carrying both is the most
   expensive kind of doc debt — two conflicting target states.
3. **Re-propagate the ODE/PDE pivot** (K4): mark the old §5 target as superseded everywhere; the two
   SymPy-facade modules (`laplace-transform.js`, `series-solution-fallback.js`) should be on a named
   kill-list, not quietly coexisting.
4. **Make the client/server decision explicit and staged** (K5): even if the kernel stays client-side
   short-term, design every kernel call as `{op, args} → serialisable result` now (it already is, via the
   seam) so Phase 8 is a transport swap, not a redesign. State this as a constraint, not a deferred
   question.
5. **Fix R10b before it ships** (K6): per-operation nerdamer reset (or per-request instance) in
   `cas-worker.js`. This is small, cheap, and the plan already names it as a product-must-fix.

### 3.3 Reshape recommendations — engine coverage/layout

1. **Normalize every engine to one shape:** real `index.html` (landing/hero) + `methods.html` (card
   index) + `methods/*.html` (feature pages) + a `assets/js/<engine>-*.js` core. Convert
   `optimization` and `graph` from inline single-pages into this pattern and give them real method
   pages + tests (E1, E6). Pick one convention for `index.html` vs redirect-stub and apply it to all 9
   (E2).
2. **Deduplicate across engines.** Merge the two least-squares modules; decide one home for eigenvalue
   material (LinAlg owns the theory pages; Numerical owns the *iterative algorithm* pages — power/inverse-
   power/QR — but cross-link them explicitly rather than duplicating). Extract shared primitives to
   `assets/js/shared/` (E3).
3. **Retire the "prototype" label.** Replace with a real maturity tier per engine (mature / mid / thin),
   derived from test coverage and page count, and surfaced on the hub so the distinction is honest (E4).
4. **Unify the header nav to all 9 engines on every page** (one-line fix, currently inconsistent) (E5).
5. **Promote PDE out of ODE subpages.** Either a sibling `engines/pde/` engine or a first-class
   `methods.html` section in ODE with its own hub cards — the plan already treats it as first-class
   (E7).
6. **Reconcile the roadmap to reality.** Flip the stale ✅/⚪ statuses (26 known Numerical mis-marks) and
   make the status derive from passing tests where possible.

## 4. Design system / UI shell

### 4.1 What exists today

- **One CSS file, `engine.css` (631 lines)** carries the whole system: tokens (`:root`), typography,
  header, buttons, corner crosshairs, cards, reveal-on-scroll, hero, workspace, forms, math keypad,
  output strips/tables. **Plus `proto/proto.css` (277 lines)** for prototype-only components (matrix
  grid, chip row, step controls, the solver "Big Box") and a **Number-Theory-only block** at the end of
  `engine.css` (sieve grid, modular heatmap, primitive-root rosette, Ulam spiral).
- **The identity mechanics** (per `DESIGN_SYSTEM.md`) are excellent and worth keeping verbatim:
  dark-only (never a light section); single-accent-per-engine via one `--electric-teal` override;
  duplicate-text hover-flip; corner-crosshair motif; reveal-on-scroll; full-bleed interactive particle
  hero; the `expo-out` `cubic-bezier(.16,1,.3,1)` on every transition. Chrome injection is centralised in
  `Engine.initChrome()` (glow spans, dup text, crosshairs, IntersectionObserver) so component markup
  can't drift between pages.
- **Vendor stack (self-hosted):** Plotly-cartesian 1.42 MB (the only plot lib, themed via
  `Engine.plotlyBaseLayout`), three.js 762 KB, math.js 670 KB, nerdamer 436 KB, KaTeX 277 KB, GSAP 143 KB.
  After a 2026-07-22 weight-reduction pass (full Plotly → cartesian-only, 67 pages migrated), vendor
  dropped 7.0 MB → 4.0 MB (~174 MB less transfer sitewide).

### 4.2 Assessment — what's good

The design system is the most consistent layer in the project. The "one shell, N accents" trick (every
component reads `var(--electric-teal)`, a page overrides it in one line) genuinely makes 9 engines read
as one identity. Centralised chrome injection is the right call. The dark-only discipline and the expo-out
curve are load-bearing identity signals.

### 4.3 Assessment — what's unwieldy (reshape targets)

| # | Issue |
|---|---|
| D1 | **`engine.css` is doing two jobs** — base system *and* a Number-Theory-specific block. Number-Theory visuals (sieve, Ulam, rosette) should be engine-scoped CSS, not appended to the base file. |
| D2 | **`proto/proto.css` vs `engine.css` split is historical**, not principled. "Prototype" components (matrix grid, solver box) are now used by mature engines (LinAlg, ODE). The split no longer reflects "prototype vs shipped." |
| D3 | **Complex V2 breaks the single-accent rule deliberately** (`--cx-domain`/`--cx-codomain` scoped to `.cx-shell`, full-bleed de-boxed layout). This is documented as a scoped exception, but it means the "one shell, N accents" claim has a real exception that should be formalised as a named variant system, not an ad-hoc `.cx-shell` escape. |
| D4 | **No design tokens file / no component library abstraction.** Tokens live inline in `engine.css :root`. There is no `tokens.css` / no documented component contract beyond `DESIGN_SYSTEM.md` (which is a snapshot, explicitly "stale if it disagrees with the code"). |
| D5 | **The solver "Big Box" / `Engine.renderClassification`** is the shared auto-solve banner, but each symbolic page still hand-wires its own panels around it. A `MethodPage` helper (flagged by the audit) would remove ~59 files of boilerplate. |

### 4.4 Reshape recommendations — design system / UI shell

1. **Split CSS by concern:** `tokens.css` (`:root` only) → `engine.css` (base components) → per-engine
   `engines/<x>/<x>.css` (scoped visuals, incl. the Number-Theory block and the `.cx-shell` exception).
   Keeps the base system shared and makes engine-specific CSS opt-in (D1, D2).
2. **Formalise the accent/variant system.** Today: one `--electric-teal` override + an ad-hoc Complex
   two-color exception. Make it a named contract: `--accent` (the per-engine slot) + an optional
   `--accent-2` for the documented Complex case, so the exception is a first-class variant, not a hack
   (D3).
3. **Introduce a `MethodPage` shell helper** that renders the common method-page skeleton (hero,
  workspace, panel, result strip, step table, classification box, plot wrap) from a small declarative
  spec per method. Removes the largest single source of page boilerplate and lets the design system
  evolve in one place (D5, ties to A1).
4. **Keep `DESIGN_SYSTEM.md` but generate the token table** from `tokens.css` so the doc stops being a
  snapshot that can rot (D4).
5. **Leave the identity mechanics untouched.** The hero, hover-flip, crosshairs, reveal, expo-out curve,
  dark-only rule are correct and are the project's strongest asset — a reshape must not touch them.

## 5. Cross-cutting reshape priorities (ranked)

If/when you greenlight changes, this is the order that maximizes leverage and minimizes risk to the
load-bearing kernel contract:

1. **Method manifest + `MethodPage` helper** (A1, A2, D5) — kills the 126 hand-stitched script lists and
   triple-registration from one source of truth. Biggest single win; no math changes.
2. **Unify the CAS to one contract with backends** (A3) — collapses the two worker stacks behind one
